## 二、API 调研结论（决定方案的关键事实）

### 2.1 流体注册：anvillib Registrum 原生支持

`dev.anvilcraft.lib.v2.registrum.builders.FluidBuilder`（anvillib-registrum sources jar）已经封装了
NeoForge 流体的全部样板。`AbstractRegistrum` 提供重载：

```java
// 最常用：名字 + 静止贴图 + 流动贴图
FluidBuilder<BaseFlowingFluid.Flowing, S> fluid(String name, ResourceLocation stillTexture, ResourceLocation flowingTexture);
FluidBuilder<BaseFlowingFluid.Flowing, S> fluid(String name, FluidBuilder.FluidTypeFactory typeFactory);
FluidBuilder<BaseFlowingFluid.Flowing, S> fluid(String name, NonNullSupplier<FluidType> fluidType);
<T extends BaseFlowingFluid> FluidBuilder<T, S> fluid(
    String name, ResourceLocation still, ResourceLocation flowing,
    FluidBuilder.FluidTypeFactory typeFactory,
    NonNullFunction<BaseFlowingFluid.Properties, T> fluidFactory);
```

`FluidBuilder.create(...)` 默认挂载：`defaultLang().defaultSource().defaultBlock().defaultBucket()`，
即一次注册会连带产出

- `NeoForgeRegistries.FLUID_TYPES` 的 FluidType（默认类型内部用 `IClientFluidTypeExtensions` 提供静止/流动贴图），
- `FluidType` 同名的 **source** 流体（本体重载 = `<name>`，注册的是 `flowing_<name>`，`FluidBuilder` 构造里 `super(..., "flowing_" + name, ...)`），
- `<name>` 的 `LiquidBlock`（方块，`BlockBehaviour.Properties.ofFullCopy(Blocks.WATER).noLootTable()` + 发光等级跟随流体，blockstate 用 `particle` 纹理），
- `<name>_bucket` 的 `BucketItem`（含 `craftRemainder(BUCKET)`、`stacksTo(1)`、generated item model），

外加可链式配置：

- `.properties { p -> ... }`：改 `FluidType.Properties`（`density/viscosity/temperature/lightLevel/canSwim/canDrown/pathType/sound/descriptionId`）
- `.fluidProperties { p -> ... }`：改 `BaseFlowingFluid.Properties`（`tickRate/explosionResistance/slopeFindDistance/levelDecreasePerBlock`）
- `.source { props -> MyFluid(props) }`：换成自定义流体类（做世界反应的入口，见 2.4）
- `.tag(FluidTags...)`：自动写 fluid tag datagen
- `.noBlock()` / `.noBucket()`：不需要可放置方块/桶时（AnvilCraft 的 honey、primordial matter 就是这种“不可放置流体”）
- `.renderType { RenderType.translucent() }`：客户端渲染层
- 返回 `FluidEntry<T>`：`getType()` / `getBlock()` / `getBucket()` / `getSource()`

> AnvilCraft 自己没用 Registrum 注册流体（`init/block/ModFluids.java` 是手写 `DeferredRegister`），
> 但 anvillib 提供了更省事的路径。**建议用 `REGISTRUM.fluid(...)`**，风格与 AnvilCraft-Wither 的
> `REGISTRUM.block/item` 一致。

### 2.2 炼药锅：**命名约定是硬约束**（本方案最重要的一条）

```java
// dev/dubhe/anvilcraft/recipe/anvil/predicate/block/HasCauldron.java:466

    ResourceLocation fluidId = BuiltInRegistries.FLUID.getKey(fluid);
    if (CompatUtil.F2C_TRANSFORM.containsKey(fluidId)) return CompatUtil.F2C_TRANSFORM.get(fluidId).get();
    ResourceLocation cauldron = ResourceLocation.fromNamespaceAndPath(namespace, "%s_cauldron".formatted(path));
    ...
}
// dev/dubhe/anvilcraft/recipe/anvil/util/WrapUtils.java:183  反向
public static ResourceLocation cauldron2Fluid(Block cauldron) {
    path = path.endsWith("_cauldron") ? path.substring(0, path.length() - 9) : "empty";
    ...
}
```

**结论：新流体必须命名为 `anvilcraft_fluid:<name>`，并且注册同名方块 `anvilcraft_fluid:<name>_cauldron`。**
只有这样，AnvilCraft 的 `HasCauldron` 谓词、`SolidLiquidRecipe`、`TimeWarpRecipe` 的
`cauldron(Block)` / `transform(Block, n)` 才能自动识别我们的锅，而不需要 mixin 或补丁。

例外通道：`dev.dubhe.anvilcraft.util.CompatUtil.F2C_TRANSFORM` 是 **public static HashBiMap**
（AnvilCraft 自己用它把 `minecraft:lava`→`lava_cauldron`、`minecraft:milk`→`milk_cauldron`），
命名不满足约定时可在这里登记。

锅相关接口（我们自定义锅时要实现的）：

### 2.3 配方：四条机制通道

| 机制 | 类型 id | 载体 / 触发 | 用于计划里的哪一条 |
| --- | --- | --- | --- |
| 多流体混合 | `anvilcraft:fluid_mixing` | **大型炼药锅**（`LargeCauldronBlockEntity.tryProcessFluidMixingRecipe`），铁砧撞击触发 | 熔融铁+熔融宝石+气态碳 → 熔融皇家钢 |
| 固液反应 | `anvilcraft:solid_liquid` | 炼药锅/大锅 + 上方铁砧撞击，物品输入 + 锅流体条件 | 熔融钨 + 下界合金碎片 → 远古残骸 |
| 时移 | `anvilcraft:time_warp` | 需下方点亮腐化信标，可带锅流体条件与 `transform` | 宝石丢进熔融宝石锅 → 宝石块（AnvilCraft 已有同类） |
| 世界流体接触 | `FluidInteractionRegistry`（非配方） | 流体流动时的邻接判定 | 熔融宝石 + 水 → 花岗岩/闪长岩/安山岩 |

**关键验证（决定成败的一条）**：`LargeCauldronBlockEntity.java:642`

```java
for (RecipeHolder<FluidMixingRecipe> holder
    : level.getRecipeManager().getAllRecipesFor(ModRecipeTypes.FLUID_MIXING_TYPE.get())) {
```

**没有任何命名空间过滤**，全库 `grep` 也没找到配方加载侧的 namespace 白名单
（唯二的 namespace 判断在客户端模型选择 `ModelBlockSelection` 与存储分类 `NamespaceCategory`）。
⇒ **附属模组自己命名空间下的 `anvilcraft:fluid_mixing` / `solid_liquid` / `time_warp` 配方会被正常加载与执行。**

`FluidMixingRecipe`（`dev/dubhe/anvilcraft/recipe/FluidMixingRecipe.java`）约束：

- 输入 2–4 条 `SizedFluidIngredient`（`requires(fluid|tag, amount)`）
- 结果 0–3 个物品 + 0–3 个流体，总计 1–6
- `consume_maximum=true` 时**只能有流体结果**（可一次吃掉尽可能多的批次）
- 输出前会 post `LargeCauldronEvent.MixingOutput` 事件（可被其他模组改写结果）

```java
// dev/dubhe/anvilcraft/data/recipe/FluidMixingRecipeLoader.java  官方写法
FluidMixingRecipe.builder()
    .requires(Fluids.WATER, 1000)
    .requires(Fluids.LAVA, 1000)
    .result(Items.OBSIDIAN, 1)
    .save(provider, "obsidian");
```

> ⚠️ **坑（必须在编码时避开）**：`save(RecipeOutput, String)` 在
> `AbstractRecipeBuilder.java:82` 里是
> `save(output, AnvilCraft.of(id).withPrefix(getType() + "/"))` —— **命名空间被硬编码成 `anvilcraft`**。
> 附属模组必须改用 `save(output, ResourceLocation)` 显式传自己的命名空间，否则配方会写进
> AnvilCraft 的命名空间（与上游冲突、且 CI 会失败）。

### 2.4 流体反应

```java
// dev/dubhe/anvilcraft/init/block/ModFluids.java:384
public static void registerFluidInteractions(FMLCommonSetupEvent ignore) {
    FluidInteractionRegistry.addInteraction(
        MELT_GEM.get().getFluidType(),
        new InteractionInformation(
            (level, currentPos, relativePos, currentState) ->      // 触发谓词
                level.getFluidState(relativePos).getFluidType() == Fluids.WATER.getFluidType(),
            (level, currentPos, relativePos, currentState) -> {    // 执行
                Block block = level.getFluidState(currentPos).isSource()
                    ? ModBlocks.CHROMATIC_STONE.get()
                    : FLOWING_MELT_GEM_CONVERTIBLE[level.getRandom().nextInt(3)]; // 闪长岩/花岗岩/安山岩
                level.setBlockAndUpdate(currentPos,
                    EventHooks.fireFluidPlaceBlockEvent(level, currentPos, currentPos, block.defaultBlockState()));
                level.levelEvent(1501, currentPos, 0);
            }));
}
```

两条路径，二选一或并用：

1. **`FluidInteractionRegistry.addInteraction`**（在 `FMLCommonSetupEvent` 里注册）：适合“流体 A 遇到流体 B 变成方块”。
   注意它的 `InteractionInformation` 自带“非 source 时随机”的世界观，可直接复用。
2. **自定义流体类覆写 `spreadTo` / `canBeReplacedWith`**：参考
   `dev/dubhe/anvilcraft/block/MeltGemFluid.java`（向下遇到水 → 变陶瓦 + `levelEvent(1501)` 冒烟），
   `FluidBuilder.source { props -> MyFluid(props) }` 注入。

## 三、需求 ↔ 现状差异（需要拍板的点）

| 计划条目 | AnvilCraft 1.6.0 现状 | 差异 / 风险 |
| --- | --- | --- |
| 熔融红宝石 / 石英 / 蓝宝石 / 黄宝石 / 绿宝石 | **只有一个 `anvilcraft:melt_gem`（熔融宝石）单流体**，不带宝石身份；`melt_gem` + 水 → 源方块 `chromatic_stone`，流动 → 随机 闪长岩/花岗岩/安山岩；`melt_gem_cauldron` + 宝石 → 宝石块（时移） | 要么我们另建 5 种独立熔融宝石流体（与上游并存），要么改造成“单流体 + 宝石类型组件”，要么直接复用上游 |
| 水反应表：熔融红宝石→花岗岩、石英→闪长岩、蓝宝石/黄玉/绿宝石→安山岩、紫水晶→方解石 | 上游只覆盖 花岗岩/闪长岩/安山岩（且是随机的），**没有方解石** | 独立流体方案可以精确实现整张表 |
| 「黄宝石」 | AnvilCraft 官方译名 `topaz` = **黄玉**（`item.anvilcraft.topaz`="黄玉"），有 **黄玉块/黄玉** 物品 | 术语需统一为「黄玉」 |
| 「石英」 | 原版只有 `nether_quartz`（下界石英）；AnvilCraft 有 `quartz_sand`（石英砂）方块、没有“石英”宝石物品 | 需确定熔融石英的原料是什么 |
| 熔融钨 + 下界合金碎片 → 远古残骸 | AnvilCraft **有**钨（`tungsten_ingot`/`raw_tungsten`/钨块）与下界合金碎片（原版） | 机制上应落到 `solid_liquid`（锅里有熔融钨 + 铁砧砸下界合金碎片），不是 `fluid_mixing` |
| 熔融铁 + 熔融宝石 + 气态碳 → 熔融皇家钢 | AnvilCraft **有**皇家钢（`royal_steel_ingot`）；有熔融宝石；**没有“气态碳”**（现有气体只有 氢/氧/氦/氘/氙/氪） | 「气态碳」需要本项目新建；或改用现有气体 |
| 反物质流体（反向流动） | AnvilCraft **只有「负物质」**（`negative_matter`，反重力），且 tooltip 明确写「负物质不是反物质」 | 命名冲突，需决定是新建「反物质」还是对齐上游叫「负物质」 |
| 浮霜液体（洗附魔） | AnvilCraft 有**浮霜金属**（frost_metal）体系与浮霜砂轮；**没有浮霜流体** | 新建流体 + 新建“洗附魔”行为 |
| 金流体清洗诅咒 → 诅咒金流体 | AnvilCraft 有诅咒金（`cursed_gold_ingot`）与诅咒金块 | 需明确“什么物品/方块经金流体变诅咒金”的语义 |
| 余烬流体（加速余烬装备修复） | AnvilCraft 有余烬金属 + 余烬铁砧（`ember_anvil` 修复/附魔） | 需要挂到余烬铁砧流程上（可能需事件/mixin） |
| 红石粉溶液（传递红石信号） | 无对应概念（AnvilCraft 红石体系是方块/EMP/压力板等） | 机制待定义：是“流体网络里可承载红石信号”还是“导电流体给相邻方块充能” |

### 4.3 风险清单

1. **上游快照漂移**：AnvilCraft 一天可能出好几个快照（本机已有 2335→2339），API 签名会变

2. **命名约定违约**：锅方块不叫 `<fluid>_cauldron` 就会静默退化成 `water_cauldron`，配方匹配不上且无报错。
3. **命名空间硬编码**：`AbstractRecipeBuilder.save(output, String)` 会写进 `anvilcraft:` 命名空间（见 2.3）。
4. **跨模组行为补丁**：若要改动上游已有流体（如 `melt_gem`）的行为，需要 mixin；
   `anvilcraft_fluid.mixins.json` 已就位，但每次上游更新都要重新核对注入点

5. **贴图工作量大**：每种流体 2 张（still/flow）× N 种流体 + 桶 + 锅；建议先做占位色块跑通逻辑。

## 六、流体 ↔ 物品反应：API 调研结论（三个特殊行为的落地依据）

**核心结论：三个行为都可以纯事件驱动实现，不需要 mixin。**

### 6.1 唯一入口：`LargeCauldronEvent.ServerTick`

```java
// dev/dubhe/anvilcraft/block/entity/LargeCauldronBlockEntity.java:183
public static void serverTick(Level level, BlockPos pos, BlockState state, LargeCauldronBlockEntity entity) {
    if (!entity.isMainPart()) return;
    ...
    entity.reforgeItemsInLava(level);
    NeoForge.EVENT_BUS.post(new LargeCauldronEvent.ServerTick((ServerLevel) level, entity));   // ← 钩子
}
```

`LargeCauldronEvent.ServerTick` 只在主部件上、每服务器 tick 发一次，携带 `ServerLevel` 与
`LargeCauldronBlockEntity cauldron`。**大型炼药锅的全部状态都通过公开访问器拿到**：

| 访问器 | 类型 | 用途 |
| --- | --- | --- |
| `cauldron.getFluids()` | `LargeCauldronFluidHandler`（`IFluidHandler` + `INBTSerializable`） | 8 个罐 × 64 B；`copyFluids()` / `setFluids(List)` / `drainStoredFluid(FluidStack, FluidAction)` / `getFluidInTank(i)` / `fill` |
| `cauldron.getTopFluid()` | `FluidStack`（已 copy） | 判断顶层流体（上游用它决定是否可点燃，`ModFluidTags.IGNITABLE`） |
| `cauldron.getInputHandler()` | `LargeCauldronInputHandler`（`IItemHandlerModifiable`） | **8 个输入槽，有公开的 `boolean mutateStackInSlot(int slot, Predicate<ItemStack> mutator)`**——原地改物品（修复/去附魔/去诅咒）的标准姿势 |
| `cauldron.getInput()/getOutput()/getOutputHandler()` | `IItemHandler` / `ItemStackHandler` | 常规物品读写（`getInput()` 在配方处理中会返回空 handler，慎用） |
| `cauldron.getFluidHandler()` | `IFluidHandler` | 同上（等价 fluids） |
| `cauldron.isIgnited()` / `setIgnited()` | `boolean` | 加热状态 |
| `cauldron.insertFromHand(held, slot)` / `extractItemsToHand(player, hand, slot)` / `insertRecipeOutput(stack)` / `hasInputMatching(Predicate)` | — | 玩家交互与产物写入 |

`LargeCauldronEvent` 其它可用子类：`EntityInside`（实体进入，含流体伤害前）、`FluidDamage`
（**可改每个流体对实体的伤害值**，setter 公开）、`UseItem`（右键，`ICancellableEvent` + 可设 `result`）、
`GiantAnvilImpact`、`MixingOutput`（可改写混合产物）。
鱼缸侧有 `FishTankEvent.*` 对应实现（`FishTankBlockEntity:376` 也调用了火中重铸）。

### 6.2 余烬流体加速余烬装备修复

上游现成工具（**public，可直接调用**）：

```java
// dev/dubhe/anvilcraft/util/FireReforgingUtil.java
public static final int LAVA_REPAIR_PER_TICK = 10;
public static boolean repair(ItemStack stack, int amount, Level level, @Nullable BlockPos pos);
// 内部：stack.has(ModComponents.FIRE_REFORGING) && stack.isDamaged() → 减 damageValue + TriggerUtil.fireReforge
```

上游的“岩浆里自动修复”（`LargeCauldronBlockEntity.reforgeItemsInLava`，private）只认
`fluid.is(Fluids.LAVA)`，速率 `LAVA_REPAIR_PER_TICK = 10`/tick。

**我们的实现**：在 `ServerTick` 监听里检测锅内是否含 `anvilcraft_fluid:ember_fluid`（按 mB 比例消耗），
对 8 个输入槽调用 `mutateStackInSlot { FireReforgingUtil.repair(it, EMBER_REPAIR_PER_TICK, level, pos) }`，
`EMBER_REPAIR_PER_TICK` > 10 即为“加速”。**零 mixin、与上游岩浆修复叠加不冲突。**

> 注意：余烬铁砧（`EmberAnvilBlock` + `EmberAnvilMenu extends AnvilMenu`）是 **GUI 内**的修复/附魔流程，
> 世界侧插不上手；因此“加速修复”落在**炼药锅**这一侧是唯一干净的做法。

### 6.3 金流体清洗诅咒 → 诅咒金流体

上游已有可直接照搬的判定/移除逻辑（在 `TranscendenceGrindstoneMenu` / `RoyalGrindstoneMenu` 里，private）：

```java
public static final int GOLD_PER_CURSE = 16;                     // RoyalGrindstoneMenu:36
private int countCurses(ItemStack stack)                          // 按 EnchantmentTags.CURSE 计数
private int removeCurses(ItemStack stack, int amount)             // ItemEnchantments.Mutable.removeIf(...)
private static List<DataComponentType<ItemEnchantments>> getEnchantmentTypes()   // ENCHANTMENTS + STORED_ENCHANTMENTS
```

**我们的实现**：锅内为 `molten_gold` 时，扫描输入槽，对每个带 `#minecraft:curse` 附魔的物品，
每移除 1 条诅咒消耗 `GOLD_PER_CURSE`(=16) mB 熔融金（或自定义值），并把等量的
**`anvilcraft_fluid:cursed_gold`（新流体）** `fill` 回锅内——“流体吸收了诅咒”。
产出流体可直接对应上游的诅咒金材料（`anvilcraft:cursed_gold_ingot`），便于后续做浇铸/凝固配方。

### 6.4 浮霜液体洗去附魔

同一套钩子；区别是把**全部附魔**（而非仅诅咒）从物品上摘掉：

- 摘除：`ItemEnchantments.Mutable` + `stack.set(DataComponents.ENCHANTMENTS/STORED_ENCHANTMENTS, ...)`
- 消耗：`frost_fluid` 按“每条附魔 X mB”扣减
- 可选玩法：附魔不凭空消失 → 若输入槽里同时有书，则把附魔写入 `enchanted_book`
  （上游 `TranscendenceGrindstoneMenu.createTransferResult()` 是现成的转移实现，可直接照抄思路）

> 三个行为共用一个 `ServerTick` 监听器与一套“检查锅内流体 → 遍历 8 个输入槽 → 改物品 → 扣流体”的框架，
> 建议抽成 `AbstractCauldronItemReaction`（`fluidPredicate / perItemFluidCost / apply(stack) / onConsume`），
> 后续加新行为只需实现一个子类。**速率控制**用 `AddonConfig.reactionInterval`（多少 tick 处理一次）避免每 tick 全量扫描。

### 9.1 文件清单与路径

| 流动流体 | `.../textures/block/molten_gem_flow.png`<br>`.../textures/block/molten_metal_flow.png` | **32 宽 × 32×N 高**（N 帧） | ✅ tint | 世界流体流动面；**带动画** |
| 桶身 | `.../textures/item/bucket.png` | **16×16** | ❌ 不染色 | 普通灰色铁桶，**不需要画灰度**；透明背景；全模组共用 |

`<name>` = `molten_ruby` / `molten_quartz` / `molten_sapphire` / `molten_topaz` / `molten_emerald` /
`molten_iron` / `molten_gold` / `molten_copper` / `molten_tungsten` / `molten_royal_steel`。

### 9.2 灰度图的约定（重要）

三个载体都是"贴图 × 颜色"相乘，所以：

- **必须 R = G = B**（真灰度），不要带色偏；
- **最亮处接近纯白 `#FFFFFF`**，表示"这里就是纯目标色"；越暗越深；
- **不要用纯黑**（相乘后仍是黑，会出现死斑）；
- 建议整体亮度偏高（平均 0xE0 以上），与染色相乘后仍然鲜亮；
- 发光不用画，由 `FluidSpec.lightLevel` 控制（熔融金属建议 10~14）；
- **`<name>_bucket.png`（桶身）不受这套约束**——它不参与染色，按普通铁桶画即可。

桶是**双层模型**（共用一个模板 + 每种流体一个一行子模型）：

`models/item/bucket_template.json`

```json
{
  "parent": "minecraft:item/generated",
  "textures": {
    "layer0": "anvilcraft_fluid:item/bucket",
    "layer1": "anvilcraft_fluid:item/bucket_fluid"
  }
}
```

`models/item/<name>_bucket.json`

```json
{ "parent": "anvilcraft_fluid:item/bucket_template" }
```

`item/generated`（→ `builtin/generated`）按层号给 `tintindex`（与皮革盔甲同机制），
所以 layer1 就是液体那层，由物品颜色处理器染 `spec.tint`。

### 9.3 动画规范（用户要求：流动动画）

两张流体图都是**竖直帧条**：宽度固定（16 / 32），高度 = 宽度 × 帧数，第 0 帧在最上面。
配套同名 `.mcmeta` 由代码侧提供，**帧数你随便定，不用告诉我**——
MC 是按 `高度 / 宽度` 自动算帧数的，改帧数不用改任何配置：

```json
{
  "animation": {
    "frametime": 2,
    "interpolate": true
  }
}
```

- `frametime` = 每帧持续多少 tick（2 = 0.1 秒/帧，与原版水一致；越慢越"稠"，熔融金属可用 3~4）。
- `interpolate: true` = 帧间插值平滑，熔融流体观感更好（原版 `warped_stem`、`stonecutter_saw` 等都用它）。
- **循环是从最后一帧接回第 0 帧**，所以最后一帧要能自然过渡到第一帧；
  想要更长循环可以画 N 帧然后让我配 `"frames": [0..N-1, N-2..1]`（原版岩浆就是这么做的来回摆动）。

已知的参考（从原版资源里核对）：原版 `water_still` 用 `{"animation":{"frametime":2}}`（隐式帧数），
`lava_still` 用 20 帧 + 来回播放的 `frames` 列表，`lava_flow` 用 `frametime: 3`。

**炼药锅液面会自动跟着动**——它用的是同一张 `<name>_still`，而方块模型的贴图走图集动画，天然会动。

**无缝要求**：`_still` 除了左右要能平铺，动画在时间上也要无缝（帧条首尾相接不跳）；

### 10.3 踩到的坑（已修，后续别再犯）

1. **Registrum 的 `FluidEntry.get()` 返回的是 `flowing_<name>`**，源流体挂在 `getSource()` 上。
   配方/桶/锅内容必须用 `fluid.getSource<BaseFlowingFluid.Flowing>()`（本项目封装为 `RegisteredFluid.source`），
   否则配方里会写出 `anvilcraft_fluid:flowing_molten_iron` 这种永远匹配不上的 id。
2. **`src/main/resources` 与 `src/generated/resources` 不能放同名文件**（`processResources` 会报
   duplicate 错误）。最终约定：**blockstate / 战利品表交给 datagen**，
   `src/main/resources` 只放**模型**（模型要引用我们自己的灰度贴图，用 `ExistingModelFile` 指向它）
   与 `lang/zh_cn.json`、`textures/**`、`mixins.json`。
3. **锅没有物品形式**，必须补 `.loot { tables, block -> tables.dropOther(block, Items.CAULDRON) }`，
   否则 Registrum 会生成 `name = minecraft:air` 的空战利品表。
4. Registrum 的 `BlockBuilder` **没有 `build()`**，`.blockstate{}.register()` 直接连着写。
5. Kotlin 里 `0xFFE23A4E` 是 `Long`，`FluidSpec.tint` 是 `Int`——统一走 `argb(...)` 辅助函数。
6. **自己调用 `FluidBuilder.bucket()` 后必须自己 `.register()`**：`create()` 里的 `defaultBucket()`
   会在 `FluidBuilder.register()` 内部调用 `bucket().register()`；一旦我们手动 `bucket()`
   （为了换成双层模型），`defaultBucket` 变 false，自动注册就不发生了，
   Registrum 会直接抛 `IllegalStateException: Found unused register callbacks`。
7. `FluidBuilder.bucket()` 要求 `source` 已存在，而 `create()` 的 `defaultSource` 要等到 `register()`
   才建源流体——所以换双层桶时必须显式 `.source { properties -> BaseFlowingFluid.Source(properties) }`。
8. **默认创造标签页必须在任何物品注册之前设置**。`AbstractRegistrum#item(...)` 在创建物品 builder 时
   读一次 `defaultCreativeModeTab` 并写进 `.tab(...)`，其字段默认值是 `CreativeModeTabs.SEARCH`：
   设晚了物品只会落到**原版搜索页**，自己的栏空的，且**没有任何报错**。
   本模组的桶是 `FluidBuilder.bucket()` 内部创建物品的，所以
   `AddonItemGroups.register(modEventBus)`（触发 `REGISTRUM.defaultCreativeTab(TAB_KEY)`）
   必须排在 `AddonFluids.register()` **前面**（[AnvilCraftFluid] 的 init 块已按此排序，
   datagen 日志里的 `Default creative tab set to …` 早于 `Registered 10 AnvilCraft fluid(s)` 即为证据）。
9. `DeferredRegister.register(String, lambda)` 在 Kotlin 下会与 `Function<ResourceLocation, T>` 重载歧义，
   必须写成 `register(name, Supplier { ... })`。

### 11.2 为什么不用 NeoForge 的 `FluidInteractionRegistry`

反查 NeoForge 21.1.241 字节码得到的结论：

- `FluidInteractionRegistry.canInteract(Level, BlockPos)` 只被
  `LiquidBlock#onPlace` 与 `LiquidBlock#neighborChanged` 调用（都是方法第一条指令）；
- 它遍历 `LiquidBlock.POSSIBLE_FLOW_DIRECTIONS`，NeoForge 官方注释写明
  **"all directions, besides DOWN, is tested"**——即它**不检查自己上方**，
  「水浇在熔融宝石上」这种情况永远不触发；
- 官方注释把这一路推给 `FlowingFluid#spreadTo`，也就是要再写一套流体子类。

所以改成继承 `LiquidBlock` 自己实现 `block/ReactiveLiquidBlock.kt`：
**`onPlace` + `neighborChanged` 六向全查**，一套代码覆盖全部情形：

| 玩家操作 | 触发 |
| --- | --- |
| 熔融宝石流到水边 | `onPlace` / `neighborChanged` |
| 熔融宝石放在水面上 | `onPlace`（下方是水） |
| 往熔融宝石上浇水 | 水在上方落位 → `neighborChanged`（上方是水） |

注册方式是 `FluidBuilder.block { fluid, properties -> ReactiveLiquidBlock(fluid, properties, product) }`；
⚠️ 自己调用 `block()` 后 `defaultBlock` 变 false，**必须自己 `.register()`**（同桶那个坑）。

## 十三、首次实机反馈与修复（用户在游戏里验证）

用户实测（创造模式，用大型炼药锅与鱼缸）反馈了五点，本节记录处理结果。

### 13.1 修：流体倒不进（单方块）炼药锅

**现象**：流体能放进大型炼药锅和鱼缸，但**倒不进我们的 `<name>_cauldron`**。

**根因（两层）**：

第一层：`CauldronFluidContent`（我们在 [CauldronFluidContentRegistry] 里登记过）
**只做两件事**（反查 NeoForge 源码确认）：

1. 锅 ↔ 流体的信息映射（`getForBlock` / `getForFluid`、`totalAmount` / `maxLevel` / `currentLevel`）；
2. 给锅方块注册 `Capabilities.FluidHandler.BLOCK` → `CauldronWrapper`（**给管道 / 机器用的**）。

它**不负责桶的交互**。桶进锅走的是原版 `CauldronInteraction`：
`AbstractCauldronBlock#useItemOn` 拿手里的物品去 `this.interactions.map().get(item)` 查表，
查不到就 `PASS`，接着桶的 `useOn` 把流体**倒在地图上**——表现就是"倒不进炼药锅"。

第二层（第一次修复没生效的原因）：**原版把交互表按锅的种类分开了，空锅用的是另一张表**：

| 锅 | 查的表 |
| --- | --- |
| `minecraft:cauldron`（**空锅**） | `CauldronInteraction.EMPTY` |
| `minecraft:water_cauldron` | `CauldronInteraction.WATER` |
| `minecraft:lava_cauldron` | `CauldronInteraction.LAVA` |
| `minecraft:powder_snow_cauldron` | `CauldronInteraction.POWDER_SNOW` |
| 我们的 `<name>_cauldron` | 注册时 `newInteractionMap` 出来的那张 |

只往"我们自己的锅"那张表加条目是没用的——玩家是拿着桶右键**空锅**。

**修复**（`event/CauldronInteractions.kt`）：把条目同时塞进**上面 4 张原版表 + 我们自己那张**。

| 手持 | 目标 | 行为 |
| --- | --- | --- |
| `<name>_bucket` | 不是同种满锅（空锅/水锅/岩浆锅/细雪锅/别的流体的锅） | 原版 `CauldronInteraction.emptyBucket` → 换成对应满锅 |
| `<name>_bucket` | 已经是同种满锅 | 吃掉点击，不重复消耗桶 |

**为什么必须等 `FMLCommonSetupEvent`**：条目要以桶物品实例为键，而桶是注册流体时由
`FluidBuilder.bucket()` 创建的；mod 构造阶段注册表未填充，`fluid.getSource().bucket`
会抛 `unbound value`。交互表是运行时查的，晚填没问题。

> ⚠️ 教训：**`CauldronFluidContent` ≠ 桶交互**；而且**交互表是按锅的种类分的**，
> 想让桶能被"空锅"接受，必须往 `CauldronInteraction.EMPTY` 里加。

### 13.2 增：浮霜洗附魔会产出「液态附魔」

洗下来的附魔不再凭空消失，而是按**同量**变成上游 AnvilCraft 的
`anvilcraft:liquid_enchantment`（`ModFluids.LIQUID_ENCHANTMENT`）——
**不挂任何具体魔咒组件**（不设 `ModComponents.LIQUID_ENCHANTMENT`），
所以它就是"无特定魔咒"的通用附魔流体。

即：洗掉 N 条附魔 → 消耗 `N × frost_fluid_per_enchantment` mB 浮霜液体 +
产出同量液态附魔。

### 13.3 增：洗空的附魔书变回普通书

`mutateStackInSlot` 只能原地改物品、改不了**物品类型**，所以走 `setStackInSlot` 事后替换；
而 `LargeCauldronInputHandler#setStackInSlot` 遇到"跨槽重复物品"会抛
`IllegalArgumentException`，因此先 `isItemValid` 问一句——
别的槽已经有普通书时保持原样，不冒险崩。
熔融金祛咒那条路径也同样处理（只剩诅咒的附魔书被洗空后也会变回书）。

### 13.4 待确认：余烬 / 浮霜液体的消耗规则

用户表述为「余烬液体和浮霜液体均**不消耗自身**，**除非是在反应容器中**」。

当前实现的实际情况：

| 场景 | 是否消耗 |
| --- | --- |
| 作为世界流体流动 / 接触水 | **不消耗**（这两种不在水反应表里，`WaterReactions.TABLE` 只含 6 种熔融宝石） |
| 倒进大型炼药锅但**没有可反应的物品** | 不消耗（无反应发生） |
| 在大型炼药锅里**发生反应** | **消耗**（`gold_fluid_per_curse` / `frost_fluid_per_enchantment`） |
| 鱼缸 / 普通容器 | 不消耗 |

也就是说：**只有"反应容器（大型炼药锅）"里发生反应时才会消耗**，与用户描述一致。
若用户的本意是"连反应时也不该消耗"，需要改 `CauldronItemReactions` 里的 `consume` 调用。

### 13.5 暂不处理

- 金属族贴图的半透明像素（用户决定暂时不管）。流体的默认渲染层是 `RenderType.solid()`，
  会忽略 alpha，因此金属现在渲染为不透明；将来想让它半透明就给该族加
  `FluidBuilder.renderType { RenderType.translucent() }`。

## 十四、第二轮实机反馈与修复

用户第二轮实测反馈：①依然放不进炼药锅；②流动熔融金属 → 石头不需要；
③诅咒金 / 浮霜 / 余烬的**物品贴图缺少**；④三个行为也不正常。

### 14.1 修：依然放不进炼药锅

见 13.1 的"第二层根因"——**空锅查的是 `CauldronInteraction.EMPTY`**，
第一次修复只补了我们自己那张表。现已同时补进 4 张原版表。

### 14.2 改：流动熔融金属不再凝固

用户明确否掉"流动 → 石头"。现在 `WaterReactions` 里金属的 `flowingProduct = null`：

| 熔融流体 | 源方块 + 水 | 流动 + 水 |
| --- | --- | --- |
| 铁 / 金 / 铜 / 钨 | 铁矿 / 金矿 / 铜矿 / 深层钨矿石 | **不反应** |
| 6 种熔融宝石 | 花岗岩 / 闪长岩 / 安山岩×3 / 方解石 | 同左（保留现状） |

### 14.3 修：4 种流体的桶模型缺失（"物品贴图缺少"）

**根因**：桶的物品模型原来是**手写 JSON**（`models/item/<name>_bucket.json`，内容都是
`{"parent": "anvilcraft_fluid:item/bucket_template"}`），而每次新增流体都要记得补文件——
`molten_amethyst`、`frost_fluid`、`ember_fluid`、`cursed_gold_fluid` 这 4 个就是漏的。
缺模型 ⇒ 物品在背包 / JEI 里显示为缺失模型。

**修复（根治漂移）**：桶模型与锅模型统统改成 **datagen 生成**，
`src/main/resources` 只留 `item/bucket_template.json` 这一个手写模板：

```kotlin
// 桶：一行子模型
builder.bucket().model { ctx, provider ->
    provider.withExistingParent(ctx.name, AnvilCraftFluid.of("item/bucket_template"))
}.register()

// 锅：父级原版 template_cauldron_full + content 指向族贴图
.blockstate { ctx, provider ->
    provider.models().getBuilder("${spec.name}_cauldron")
        .parent(cauldronTemplate(provider))
        .texture("content", AnvilCraftFluid.of("block/${spec.family.textureBase}_still"))
        ...
}
```

这样**新增流体不可能再漏模型**。验证脚本已确认：`lang 里桶数 14 == 桶模型文件数 14`。

> ⚠️ 教训：**每种流体都会派生的资源（模型 / blockstate / lang / loot）一律交给 datagen**，
> 手写清单式生成（脚本里硬编码流体名）必然随新增内容漂移。

### 14.4 修：原本正常的水反应全部失效（严重回归）

**现象**：用户反馈"原本有的流体反应消失了，新的反应也不生效"——即宝石族的水反应也没了。

**根因**（我在 15f36d5 引入的回归）：为了区分源/流动，`ReactiveLiquidBlock` 改成用
`BuiltInRegistries.FLUID.getKey(this.fluid).path` **反推自己的名字**再查表。
但 `Registrum` 的 `FluidBuilder.block(factory)` 传进去的是**流动流体**：

```java
final NonNullSupplier<T> supplier = asSupplier();           // ← 流动流体
... block(this, sourceName, p -> factory.apply(supplier.get(), p))
```

于是查到的名字是 `flowing_molten_ruby`，`WaterReactions.TABLE` 里没有这个键
→ **所有反应一起静默失效**。

**修复**：不再让方块反推名字。`AddonFluids` 用权威的 `spec.name` 查好反应对象，
直接构造给方块：

```kotlin
val reaction = WaterReactions.reactionFor(spec.name)!!
builder.block { fluid, properties -> ReactiveLiquidBlock(fluid, properties, reaction) }.register()
```

**顺带确认了源/流动的判定是对的**（反查 `LiquidBlock` 字节码）：

- `LiquidBlock.LEVEL` 是 `BlockStateProperties.LEVEL`（**0~15**）：**`LEVEL == 0` 才是源方块**，1~7 流动，8 下落；
- `getFluidState(state)` 是 `stateCache.get(min(LEVEL, 8))`，而
  `stateCache = [getSource(false), getFlowing(7)…getFlowing(1), getFlowing(8,true)]`
  → 只有 `LEVEL == 0` 命中下标 0（源），所以 `FluidState#isSource` 恰好只对源方块为真 ✓。

### 14.5 增：启动自检（诊断"反应不生效"）

`event/ReactionTableCheck.kt` 在 `FMLCommonSetupEvent` 把水反应表逐条解析并打进日志
（此时注册表已填充，解析上游方块安全）：

```
Water reaction table (10 fluid(s)):
molten_ruby            source -> minecraft:granite              | flowing -> minecraft:granite
molten_iron            source -> minecraft:iron_ore             | flowing -> (不反应)
molten_tungsten        source -> anvilcraft:deepslate_tungsten_ore | flowing -> (不反应)
```

它同时兜住"产物表里误写直接 `.get()` 而非包 lambda"这类问题——会在启动时立刻炸，
而不是等玩家倒水时才崩。
